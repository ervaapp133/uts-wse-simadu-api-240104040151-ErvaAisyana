1. Analisis Kebutuhan dan Perancangan REST API (Soal 1 — 15 Poin)

1.1 Identifikasi Aktor & Resource

  • Mahasiswa (role: mahasiswa): Mengajukan pengaduan baru, melihat daftar dan detail pengaduan miliknya sendiri, serta mengubah atau menghapus pengaduannya sendiri selama status masih diajukan.
  • Administrator (role: admin): Melihat seluruh pengaduan mahasiswa dan memperbarui status penanganan (diajukan, diproses, selesai) tanpa mengubah identitas pemilik (mahasiswaId).
  • Resource Utama: auth (autentikasi login) dan pengaduan (atribut: id, mahasiswaId, judul, kategori, deskripsi, status, createdAt).

2. Implementasi REST API & Mekanisme Keamanan (Soal 2 & 3 — 50 Poin)

  • Express 5 Layered Architecture: Memisahkan routes, middleware, controllers, services, dan repositories sesuai struktur proyek yang direkomendasikan.
  • Hashing Password (Scrypt + Salt): Password akun demo disimpan dalam format salt:derivedKey di src/repositories/user.repository.cjs dan diverifikasi menggunakan crypto.timingSafeEqual (src/utils/password.cjs).
  • JWT Bearer Token + Expiry: Setiap login menerbitkan token unik yang ditandatangani dengan JWT_SECRET dan masa berlaku JWT_EXPIRES_IN=1h.
  • Kontrol Akses Berlapis: RBAC melalui authorizeRoles, validasi kepemilikan mahasiswaId === req.user.id, dan penguncian pengubahan/penghapusan hanya saat status diajukan.
  • Validasi Ketat & Global Error Handler: Menolak JSON rusak, input kosong, kategori/status tidak valid, serta field terlarang (id, mahasiswaId, status, createdAt) dari sisi client.

4. Jawaban 10 Pertanyaan Demonstrasi UTS (Bagian F)

1. Apa perbedaan autentikasi dan otorisasi? Tunjukkan implementasinya di dalam kode. Autentikasi memverifikasi siapa pengguna yang mengakses sistem; diimplementasikan pada auth.service.cjs (verifikasi password hash & penerbitan JWT) dan auth.middleware.cjs (authenticateBearer). Otorisasi menentukan apa yang boleh dilakukan pengguna; diimplementasikan pada authorize.middleware.cjs (authorizeRoles) dan pengecekan kepemilikan/status di pengaduan.service.cjs.
2. Mengapa mahasiswa yang berhasil login belum tentu boleh mengakses semua endpoint? Login hanya membuktikan identitas (autentikasi), bukan memberikan hak akses penuh. Berdasarkan prinsip Least Privilege, mahasiswa hanya boleh mengelola pengaduannya sendiri demi privasi data, sedangkan perubahan status penanganan merupakan wewenang eksklusif Administrator.
3. Apa perbedaan respons HTTP 401 dan 403? 401 Unauthorized berarti identitas pengguna belum terverifikasi (tanpa token, token palsu/kedaluwarsa, atau kredensial login salah). 403 Forbidden berarti identitas sudah sah, namun role atau kepemilikan data tidak mengizinkan operasi yang diminta.
4. Bagaimana API memastikan seorang mahasiswa hanya dapat mengubah pengaduannya sendiri? mahasiswaId diambil dari req.user.id hasil dekode JWT server (bukan dari body client), middleware menolak field mahasiswaId pada payload, dan pengaduan.service.cjs memverifikasi existing.mahasiswaId === currentUser.id serta existing.status === 'diajukan' sebelum mengizinkan pembaruan.
5. Mengapa password harus di-hash dan mengapa token tidak boleh dicatat ke log? Password di-hash satu arah dengan salt acak (Scrypt) agar tidak dapat dibaca kembali bila terjadi kebocoran data. Token tidak boleh dicatat ke log karena token adalah kunci akses aktif; jika bocor di log, pihak lain dapat menyamar sebagai pengguna tersebut. Karenanya, security.middleware.cjs menyamarkannya sebagai Auth:[REDACTED].
6. Bagaimana sebuah input yang salah ditangani oleh middleware dan error handler? JSON rusak ditangani globalErrorHandler (400 INVALID_JSON). Input kosong, tipe salah, atau field terlarang ditolak lebih awal oleh validate.middleware.cjs dengan AppError(400) sebelum masuk ke controller/service, lalu diformat seragam tanpa membocorkan stack trace.
7. Apa perbedaan HTTPS dengan autentikasi Bearer Token? HTTPS (TLS) mengenkripsi jalur transmisi jaringan agar data tidak disadap di perjalanan, sedangkan Bearer Token memverifikasi identitas dan hak akses pengguna pada lapisan aplikasi. Keduanya saling melengkapi.
8. Bagaimana membuktikan bahwa input yang ditolak tidak mengubah data? Dengan membaca kondisi data sebelum dan sesudah request ilegal menggunakan GET /api/pengaduan. Karena request yang gagal validasi atau otorisasi langsung dihentikan pada middleware/service sebelum memanggil pengaduan.repository.cjs, jumlah dan isi data terbukti tetap tidak berubah.
9. Mengapa dokumentasi Swagger yang tampil belum cukup membuktikan API berjalan dengan benar? Swagger UI hanya menampilkan kontrak statis dari openapi.json. Tampilan dokumentasi tidak menjamin bebas bug logika, validasi, atau celah otorisasi di kode backend; pembuktian tetap membutuhkan pengujian aktual untuk skenario sukses maupun gagal.
10. Apa yang harus diperbaiki agar layanan ini layak diterapkan pada lingkungan produksi? Migrasi ke database persisten (PostgreSQL/MySQL), wajib HTTPS/TLS, manajemen secret terpusat, penambahan rate limiting pada login untuk mencegah brute-force, mekanisme refresh token & revocation (Redis), pembatasan origin CORS ketat, serta logging terstruktur dan audit trail perubahan status.
